# Dungeon Game

ファミコン時代の Wizardry・女神転生を思わせる、グリッド型の3Dダンジョン探索ゲーム(Swift / SwiftUI)。
A・B・Cの3人で、AIを活用しながら開発する。

## 最初に読むもの

`docs/` の仕様書を、人もAIも必ず参照する。優先順位は **仕様書 ＞ UI・画面イメージ ＞ 設計 ＞ 現在の正式コード ＞ AIの提案**。

| 文書 | 内容 |
|---|---|
| `docs/02_ゲーム仕様書.md` | ゲームの仕様(操作、面、T・K・G、マップ定義) |
| `docs/03_開発ロードマップ.md` | フェーズと完了条件 |

※ 現在のリポジトリで確認できる文書に合わせて掲載しています。未配置の開発規約・UI仕様書・AI作業手順書・進捗記録などは、内容を確認せずに新規作成・復元しません。

## ソースの構成と担当

| フォルダ | 内容 | 担当 |
|---|---|---|
| `Map/Core/` | 向き・位置・プレイヤー・ゲーム状態・ゲーム進行 | A |
| `Map/Stage/` | マップ(マス、読み込み、各面の定義) | A |
| `Map/Rendering/` | 3Dダンジョン描画 | A |
| `Map/AutoMap/` | オートマップ | A |
| `Map/UI/` | 画面・コマンド | A |
| `Map/Events/TileEvent.swift` | マスの特殊処理の入口 | A |
| `Map/Events/Trap.swift` | T:トラップ | B |
| `Map/Events/Key.swift` | K:鍵・G:ゴール | C |

担当外のファイルは、担当者に依頼して変更する。

※ BとCは未定のため、`Map/Events/Trap.swift`(B担当)と `Map/Events/Key.swift`(C担当)は、決まるまで、Aが暫定で担当する。決まったら、変更内容を共有して、引き継ぐ。

## 開発の流れ

1. `main` から作業用ブランチを作る(例: `feature/trap`、`fix/render-corner`)。
2. 小さな単位で変更し、コミットする(1機能・1変更)。
3. プルリクエストを作る。テンプレートの「AI変更報告」と検証状況を記入する。
4. **別の人**が確認してから、`main` へ統合する。
5. 統合後は、既存機能の回帰確認を行う。

`main` は、常に「正式採用済みで動くコード」に保つ。

## 1. 目的

本ロードマップは、3名の開発者（A・B・C）がAIを活用しながら、仕様を崩さず段階的にゲームを完成させるための開発順序と各段階の完了条件を定める。

## 2. 開発原則

-   前工程が完了してから次工程へ進む。
-   「実装した」ではなく「検証して仕様どおり動作した」ことを完了条件とする。
-   AI生成コードは正式採用コードと区別する。
-   各担当者は担当外のコードを独断で変更しない。
-   統合前に変更内容・影響範囲・検証結果を共有する。
-   既存機能を壊していないことを回帰テストで確認する。

## 3. 担当

### A：コア・統合担当

-   ゲーム全体の管理
-   Player / GameState / GameManager
-   MapData / MapCell / MapLoader
-   基本移動
-   3Dダンジョン描画
-   オートマップ
-   UI・コマンド
-   スタート画面・面の選択・画面遷移・ギブアップ
-   B・Cの機能統合
-   最終動作確認

### B：トラップ担当

-   Trap.swift
-   トラップのデータ・処理
-   Tへの配置
-   Aのゲーム進行への統合
-   テスト

### C：鍵・ゴール担当

-   Key.swift
-   鍵・宝箱の処理
-   Kへの配置
-   Gの判定（面ごとの鍵要否を含む）
-   Aのゲーム進行への統合
-   テスト

## 4. フェーズ

### Phase 0：仕様確定

担当：全員 - 開発規約を確認 - ゲーム仕様を確認 - UI仕様を確認 -
3D完成イメージを確認 - 担当範囲を確定

完了条件： - 3人が同じ仕様書を使用している -
不明点・矛盾点が解消されている

### Phase 1：コアゲーム

担当：A

-   プレイヤーの位置・方向
-   グリッド移動
-   壁による移動制限
-   マップ読み込み（チュートリアル・試練の迷宮・ランダムステージ。面ごとの初期方向・鍵の要否を含む）
-   Sの開始位置
-   スタート画面と面の選択（見た目は最小限とし、Phase 7で調整する）
-   画面遷移（スタート画面 → プレイ画面 → クリア表示 → スタート画面）
-   ギブアップ（確認表示を含む）

完了条件：

-   Sから正常に移動できる
-   壁を通過しない
-   方向転換が正しい
-   スタート画面からチュートリアルと試練の迷宮を開始できる
-   面を選び直したとき、前回のプレイの状態が残っていない
-   ギブアップで、確認のうえスタート画面に戻れる
-   実機で確認済み

十字路 6. 突き当たり 7. 部屋

### Phase 3：オートマップ

現在位置を表示 - プレイヤー方向を表示 - 未探索領域を表示しない

完了条件： - 実際に歩いた範囲だけがマップに記録される -
未到達のT/K/Gなどが先に表示されない - 3D表示とマップ情報が矛盾しない

### Phase 4：トラップ

それ以外の移動機能が壊れていない

### Phase 5：鍵・ゴール

担当：C

-   Key.swift
-   K配置
-   鍵取得
-   G判定（面ごとの鍵要否に従う）

完了条件：

-   Kで鍵を取得できる
-   鍵取得状態が保持される
-   鍵が必要な面（試練の迷宮）で、鍵なしでGに到達してもクリアにならない
-   鍵が必要な面（試練の迷宮）で、鍵ありでGに到達するとクリアできる
-   チュートリアルで、段階案内に従って鍵を取得し、Gに到達するとクリアできる

### Phase 6：統合テスト

担当：A＋B＋C 基本シナリオ： S → 探索 → T → K → G（試練の迷宮）。あわせて、チュートリアル面の段階案内に従って S → K → G を確認する。

確認項目： - 移動 - 方向転換 - 3D表示 - オートマップ - T - K - G -
鍵状態 - UI - 既存機能への影響

完了条件： - 一連のゲーム進行を最初から最後まで実機で確認できる -
致命的な不具合がない

担当：A中心、全員確認 - 3D表示位置 - オートマップ - コマンド表示 - スタート画面 - クリア表示 -
線の太さ - 色 - 余白 - 文字サイズ - 画面全体のバランス

完了条件： - UI仕様書と完成画面イメージに一致する - 操作方法が分かる -
画面崩れがない

### Phase 8：従来機能の最終確認

担当：全員

- 来場者向け操作案内・段階式チュートリアルの確認
- 状況メッセージと円形カーソルの確認
- 石積み風3D表示と探索済みマップ色分けの視認性確認
- 宝箱・鍵取得演出とゴール扉の表示確認
- ステージBGMのループ、ギブアップ・ゴール時の停止、扉音からクリア音への順次再生を確認
- 端末の消音設定に従うことと、音声失敗ログを確認
- 実機最終確認、バグ修正、不要コード・不要ファイル整理
- Git / バックアップ、提出用スクリーンショット、発表資料、最終版の仕様書保存

完了条件： - 完成チェックリストを全項目確認済み -
正式採用コードをバックアップ済み - 提出版を確定

### Phase 9：ランダムステージとモード選択

担当：A（マップ生成、画面、統合）

- 固定マップの表示名を「試練の迷宮」に変更する。
- タイトル画面を「チュートリアル」「試練の迷宮」「ランダムステージ」の3入口に整理する。
- seed指定の再現可能な乱数で、連結した通路迷宮を生成する。
- S、鍵入り宝箱K、T、Gを各1つ配置する。鍵はSからGへの経路上に置き、Tは通路を塞がない。
- TはS-G最短経路の外に置き、鍵を取ってゴールへ向かう経路では反転しない。
- 迷路にループ通路を設け、トラップ発動後も迂回・復帰できる分岐を確保する。
- 生成したseedをプレイ画面に表示し、前回のseedによる再挑戦を用意する。
- タイトルと進行中UIを含む現行仕様・README・進捗記録のモード名をそろえる。

完了条件：

- 同じseedから同じマップ・イベント配置を生成する。
- SからKへ到達でき、鍵を取得した後にGへ到達できる。
- Tを踏んでも通路が塞がらず、方向転換で探索を続けられる。
- チュートリアルと試練の迷宮の既存動作を壊さない。
- iOS Simulator向けビルドが成功する。
- Simulatorと実機でモード選択・マップ生成・クリアまで確認する（実機確認後に完了）。

## 5. 統合ルール

-   B・Cは機能完成後、Aへ変更内容を渡す。
-   Aは統合前にバックアップを作成する。
-   統合後は必ず回帰テストを行う。
-   問題が発生した場合、直前の正式採用版へ戻せる状態にする。

## 6. フェーズ移行ルール

次のフェーズへ進む条件： - コンパイル成功 - 仕様適合 -
担当機能の動作確認 - 既存機能の回帰確認 - 必要に応じて実機確認 -
チーム内共有完了

1つでも重要な条件を満たしていない場合、原則として次フェーズへ進まない。

## 7. 進捗管理

各フェーズについて以下を記録する。

-   フェーズ名
-   担当者
-   開始日
-   完了日
-   変更ファイル
-   検証状況
-   未解決問題
-   正式採用バージョン

## 8. 完成の定義

「コードを書き終えた」ことではなく、
**仕様どおり実装され、コード検証・実機検証・回帰テストを終え、チームが正式採用した状態**
を完成とする。
